## 자동 검사 규칙

생성 agent가 chunk마다 직접 돌렸고, 최종본도 같은 검사를 통과했다.

- 형식: 허용 key만, `type`·`role` enum, 부품은 U+4E00–9FFF 또는 U+3400–4DBF의 한 글자(부수 보충·Ext-B 금지, 폰에서 □ 방지), 설명은 한국어 한 문장 70자 이하
- 음독: 공유 음독 `on`은 그 한자의 KANJIDIC2 음독이어야 한다. 부품 자체의 음독과 다르면 경고
- 계열: `series`는 공유 음독이 있을 때만, 각 글자가 같은 음독을 가져야 한다. IDS상 같은 부품이 없으면 경고
- 실사용: 공유 음독과 계열 예시 음독은 JMdict 일반 어휘에서 그 한자가 실제로 그렇게 읽혀야 한다(연탁·촉음 허용)

## 남은 한계

- "어느 부품이 의미 요소이고 어느 부품이 발음 요소인지"는 자동 검증이 안 된다. 검수한 383자 밖의 517자는 생성과 자동 검사만 거쳤다.
- 음이 갈라진 note 302개의 설명 속 읽기("寺(ジ)는 원래 발음 요소지만 음은 タイ")는 구조화된 값이 아니라 자동 검사 대상이 아니다.
- 신자체 간략형 부품(㦮, 圣, 㑒 등)은 KANJIDIC2·IDS에 없거나 음독이 비어 있어 생성·검수 쪽 지식으로만 확인했다.

## 새 단어에 해설 붙이기

- 같은 한자를 쓰는 기존 단어의 note를 그대로 복사해 `kanji_notes`에 넣는다(단어에 처음 나오는 순서). 복사본이 다르면 `TestKanjiNotes`가 실패한다.
- 새 한자는 `model.KanjiNote` 구조로 쓰고, 공유 음독은 일반 어휘에서 실제로 쓰이는지 확인한다. 확신이 없으면 넣지 않는다(버튼이 안 생길 뿐 화면은 그대로다).
- 생성·검사 스크립트는 일회성이라 저장소에 넣지 않았다.
